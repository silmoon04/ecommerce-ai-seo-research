# True Fit: a vertical benchmark for purchases that stay purchased

Research snapshot: 29 September 2026. This report assesses public evidence and proposes ten experiments; it does not claim to have run them. The companion JSON contains the full experiment, dependency, pricing and falsification record for each idea.

True Fit is a useful benchmark because it connects a specific purchase uncertainty, apparel fit, to transaction outcomes. A new entrant should consider integrating its data before rebuilding a size recommender. True Fit already markets a shopping agent, persistent profiles, personal-size filtering and dynamic size charts. Its technical materials document licensed MCP access. Merely adding an assistant to sizing guidance would enter an occupied market. [Shopping agent](https://www.truefit.com/conversation-fit-agent), [MCP integration](https://techdocs.truefitcorp.com/docs/mcp-integration).

The underlying proposition is credible: product attributes and a shopper's previous fit experience can help resolve whether a particular garment is worth buying. Cross-brand purchase and return observations provide information that public product descriptions alone cannot supply. The network also creates a difficult data-acquisition problem for a newcomer. Its coverage and scale remain vendor assertions; dataset size does not establish causal conversion lift or satisfactory fit for an unfamiliar product. [Technical specification](https://www.truefit.com/fit-intelligence-spec).

Pricing needs clarification before a commercial comparison. The vendor's Shopify page currently advertises a starting price of $1,000 monthly, while the live Shopify App Store listing displays Free. Older localized listings specified USD, but the conflicting current pages do not support one settled price. These are observations on the research date, not evidence that a full enterprise integration is free. [Vendor Shopify page](https://www.truefit.com/shopify), [App Store listing](https://apps.shopify.com/truefit).

The evidence separates into three levels.

| Evidence | What it supports | What remains unproved |
|---|---|---|
| Homepage claim of 1-2% sitewide conversion lift against A/B controls | True Fit publicly claims controlled testing | Relative versus absolute lift, allocation, sample size, uncertainty and retained-purchase effect are unspecified |
| PacSun's 12.9% conversion among True Fit shoppers; 4.71% claimed incremental revenue | A named merchant implementation with reported commercial outcomes | Tool engagement is selected behavior; the public calculation of incrementality and returns treatment is missing |
| Purchase APIs, return feeds and experiment assignments | A concrete implementation can connect treatment and transactions | Complete deployment, unbiased attribution and a positive treatment effect still require verification |

The first row comes from the [homepage](https://www.truefit.com/). PacSun's [case study](https://info.truefit.com/pacsun-case-study) reports the engaged-shopper conversion figure; a later [vendor article](https://www.truefit.com/post/why-clothing-sizes-are-inconsistent-across-brands-and-what-retailers-can-do-about-it) gives the revenue claim. Neither number should become our expected uplift.

Even endpoint names need checking. The Moosejaw case-study headline calls its 24% result an ecommerce-return reduction, while True Fit's specification describes a 24% decline in size bracketing over one year. Those are different denominators. We should preserve the ambiguity rather than cite the number as a general purchase gain. [Moosejaw case](https://info.truefit.com/moosejaw-case-study), [Specification](https://www.truefit.com/fit-intelligence-spec).

An adjacent competitor provides a better reporting example. Fit Analytics describes splitting all SNIPES traffic between Fit Finder and a static size chart, analyzing everyone assigned, and observing 645,000 shoppers over two months. It reports 3% higher conversion. This remains vendor evidence without a full statistical protocol, but the denominator is clearer than engaged-user comparisons. It does not predict the effect of our proposals. [SNIPES case study](https://fitanalytics.com/case-studies/snipes).

True Fit's web integration records order identifiers, line items, prices, sizes and quantities. Its iOS SDK documents completed-order tracking and widget callbacks. A separate weekly return feed joins original orders and includes online and in-store channels. These components make retained-purchase measurement feasible. They do not make a checkout event a retained sale: older Shopify guidance explicitly makes returns data optional. [Web orders](https://techdocs.truefitcorp.com/docs/order-confirmation-integration), [iOS SDK](https://techdocs.truefitcorp.com/docs/native-sdk-2-0-ios), [Return feed](https://techdocs.truefitcorp.com/docs/weekly-incremental-returns-feed), [Shopify data requirements](https://help.truefit.com/app-data-requirements).

The A/B event hook exposes a user's assigned experiment groups when widget rendering is attempted. It is disabled by default and needs vendor activation. This is documented experimentation infrastructure; its public guide does not reveal randomization mechanics. No public shopper-agent replay product or monitoring of third-party consumer search recommendations was found in the reviewed sources. That is a search result, not proof of internal absence. [A/B Test Tracking](https://techdocs.truefitcorp.com/docs/experiment-settings-event-hook).

Identity is a practical integration issue. True Fit instructs chat providers to synchronize authenticated retailer identities and use general guidance for unidentified guests. An anonymous visitor should not receive an invented identity to force personalization. Its privacy policy describes personal data processing and sharing, so marketing language about excluding PII from recommendation outputs should not be interpreted as an anonymous service. [Identity sync](https://techdocs.truefitcorp.com/docs/mcp-user-identity-sync), [Privacy policy](https://www.truefit.com/privacy-policy-and-choices).

The ten opportunities below are hypotheses, with incumbent overlap treated as a constraint.

1. **Carry one authorized fit decision into checkout.** Build an expiring, merchant-scoped receipt that preserves the recommended variant and fit version when an external assistant hands a shopper to a website or native app. True Fit already has identity sync and session tokens; the proposed difference is a permission-limited handoff, not another universal profile. Randomize eligible shoppers before handoff against today's deep link and measure retained purchases, including permission refusals. Wrong-account joins or repeated authorization could erase the benefit. Integration-heavy. [Identity sync](https://techdocs.truefitcorp.com/docs/mcp-user-identity-sync).

2. **Keep the recommended width and inseam available.** Revalidate the exact variant at handoff and, after add-to-cart intent, use a short merchant-supported reservation. Existing True Fit filtering and Fit Analytics alternatives already address stockouts. The added value must come from preserving an actual purchase path through checkout. Test against those existing capabilities, measure stock-pool spillovers and stop if holds merely transfer sales between shoppers. Integration-heavy. [True Fit agent](https://www.truefit.com/conversation-fit-agent), [Existing product alternatives](https://fitanalytics.com/case-studies/simons).

3. **Ask only a question that can change the decision.** Choose one optional reference-garment or fit-preference question when its answer could change the shortlist. Otherwise, proceed with existing evidence. True Fit already offers contextual conversations, so the proposed advantage is selecting questions by incremental retained-purchase value after accounting for interruption. Randomize before the question appears; questionnaire completion is not success. This can start now with a licensed fit engine and simple policy. [Conversational offer](https://www.truefit.com/conversation-fit-agent).

4. **Reset advice when a familiar garment changes.** Version fit relationships by declared cut or fabric revisions, then use corroborated outcomes to trigger targeted sample measurements. A shopper's old successful purchase should not remain decisive after the product changes. Continuous learning and dynamic charts already exist; batch-aware invalidation is the narrower hypothesis. Randomize matched product-version clusters and distinguish garment drift from a changing customer mix. Integration-heavy. [Catalog inputs](https://techdocs.truefitcorp.com/docs/mcp-catalog-and-transactions).

5. **Let an adult gift recipient share one fit permission.** A recipient could authorize a recommendation for a named merchant and category without handing the buyer a reusable body profile. Keep buyer and wearer separate when learning from the gift outcome. True Fit already supports shopping for others. The proposed difference is recipient control and transaction labeling. Randomize gift-intent buyers, count unanswered invitations, and mature outcomes through the gift return period. Specific permission and easy withdrawal need an actual implementation review. Integration-heavy. [Existing gifting support](https://www.truefit.com/shopify), [ICO consent guidance](https://ico.org.uk/for-organisations/uk-gdpr-guidance-and-resources/lawful-basis/consent/what-is-valid-consent/).

6. **Explain the fit tradeoff between two viable products.** Show a concrete difference such as waist comfort versus desired length, using verified facts and honest uncertainty. Existing alternatives and fit explanations mean a comparison interface alone is insufficient differentiation. Test whether a concise, preference-specific comparison increases retained purchases against the same candidates presented as one confident answer. Abstention can protect trust, but excessive choice or needless caution can lose purchases. Feasible now. [Fit Analytics alternatives](https://fitanalytics.com/case-studies/simons).

7. **Make an unsuitable inseam feasible through alteration.** Include an existing merchant's eligible shortening service in discovery, with finished dimensions, total price, capacity and delivery date. UNIQLO demonstrates that online alteration already exists; an agent could make that service visible to shoppers whose search otherwise has no match. Test product-only against product-plus-service discovery. Because alteration policies can restrict returns, require satisfactory-fit and remake guardrails; an unreturnable mistake is not success. Integration-heavy. [UNIQLO service](https://faq-uk.uniqlo.com/pkb_Home?fs=RelatedArticle&id=kA0Vh0000001Mui&l=en_US).

8. **Offer a human fitting check where it can rescue a purchase.** Route an unresolved shopper to qualified staff with an authorized context summary and a visible wait estimate. Generic human handoff already exists; the proposed advantage is allocating limited fitting capacity from randomized purchase evidence. Test the offer against the current assistant and include people who decline. A six-minute check at an assumed GBP 30/hour costs GBP 3, requiring 7.5 percentage points of additional retained-purchase probability if each additional purchaser contributes GBP 40, before fixed costs. These are chosen assumptions. Integration-heavy. [MCP integration](https://techdocs.truefitcorp.com/docs/mcp-integration).

9. **Replenish sizes requested by real shoppers who could not buy.** Deduplicate human-origin AI shopping intents and aggregate genuine fit-qualified stock failures. Compare a small intent-informed replenishment program with the existing buying rule at equal capital. True Fit already describes restocking uses; the difference would be verified unmet intent and controlled inventory decisions. Synthetic probes must never become demand. Randomize independent stock pools and measure category-wide retained orders after substitution and inventory carrying costs. Frontier. [Inventory use cases](https://www.truefit.com/fit-intelligence-spec).

10. **Validate which simulated fit failures predict lost purchases.** Freeze retrieval and replay diverse real intent strata against truthful, implementable fit interventions. Register predictions before merchant-controlled randomized tests, then reconcile purchases and mature returns. Only after several tests should replay scores select deployment work under an equal-budget comparison. Existing A/B tooling makes a dashboard unoriginal; evidence of simulator-to-purchase transfer would be the useful product. Integration-heavy. [Experiment assignments](https://techdocs.truefitcorp.com/docs/experiment-settings-event-hook), [Outcome reconciliation](https://techdocs.truefitcorp.com/docs/weekly-incremental-returns-feed).

Across these tests, the default primary outcome is the share of all eligible assigned shoppers who make a paid, noncancelled purchase and retain at least one eligible item after the full return window. Preserve assignment before engagement, reconcile exchanges once, and report raw orders, return rates and contribution separately. Fewer bracketed orders can be useful without creating an additional purchaser. Missing return records cannot be treated as proof of satisfaction.

The shared proxy proposal is useful for finding factual and reasoning failures. Its illustrative percentages are not measurements; fifty identical agent reruns are not fifty independent shoppers. Moving a result upward tests rank sensitivity but does not implement a ranking gain. A custom search function does not replicate proprietary consumer retrieval, personalization or checkout.

The distinction matters commercially. True Fit says conversational fit was live at Lands' End in August; its Glance collaboration schedules first experiences for the 2026 holiday season. Production availability and future announcements should not be pooled into an agent-origin conversion result. [Lands' End deployment](https://www.truefit.com/post/agentic-commerce-gets-real-at-lands-end), [Glance timing](https://www.truefit.com/post/true-fit-glance-bring-fit-intelligence-into-the-agentic-shopping-experience).

Start with one merchant that can reconcile returns and expose a controlled assistant or landing experience. Measure the actual frequency of context loss and variant failure before choosing a pilot. The JSON's prices are unvalidated willingness-to-pay tests. Its six-week or longer examples are scheduling floors, not promises of statistical power; sparse AI-origin traffic can make a useful purchase effect impossible to establish quickly.
